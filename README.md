# Hotel Cancellation Risk Scoring

: 데이터 누수(Data Leakage) 통제 기반의 예약 취소 예측

## 1. 프로젝트 요약
- 호텔 예약 데이터로 예약이 들어온 순간 그 예약이 취소될지(is_canceled) 예측
- 프로젝트 전체가 "점수가 진짜인가?"를 따라감. 누수와 중복을 정리하고, 미래 데이터로 정직하게 평가하는데 중점을 둠
 (3~4줄: 문제, 접근, 핵심 결과, 비즈니스 임팩트)

## 2. 문제 정의
- 비즈니스 문제 : 호텔은 예약 취소, 노쇼로 빈 방이 생기는 것이 손실이 된다. 취소될 예약을 예측하여 손실을 줄이는 조치를 취하고자 한다. (빈 객실, 오버부킹 판단)
- 목표 : 취소로 인한 공실 손실 줄이기
- 예측 대상 : 예약 1건이 투숙 전에 취소될 지 여부
- 목표: 무엇을 예측하고 어디에 쓰는지
- 문제 유형 : 이진 분류
- 의사결정 활용방안 : 확인 연락, 선제 재판매, 초과예약(오버부킹)
- 평가 지표
  - 정답 비율이 63:37이라 전부 '유지'라고 답해도 정확도가 63%이기 때문에 정확도를 주 지표로 사용하지 않음
   **ROC-AUC** | 주 지표. 취소 예약을 유지 예약보다 높은 순위에 두는 능력 |
| **PR-AUC** | 주 지표. 취소(양성) 클래스를 찾는 성능에 집중 |


  - PR-AUC를 같이 쓰는 이유도 하나 적어 두면 좋습니다. ROC-AUC는 유지 예약(다수)을 잘 맞히는 것까지 점수에 반영되지만, PR-AUC는 취소를 찾는 성능만 봅니다. 두 지표가 같은 방향이면 결론이 더 믿을 만합니다.
  - 확률 보정 항목은 03에서 "모델이 확률을 과소 추정한다"는 결과와 날짜별 건수가 16% 적게 나온 결과를 미리 예고하는 장치입니다. 순위 지표만 좋다고 끝이 아니라는 걸 보여 줍니다.
  - 확인 연락은 취소를 놓치는 비용이 비싸다
  - 재판매는 잘못 판 방이 비싸다 (고객이 오면 방이 없으니까)
  - 그러므로 0.5 하나로 고정하면 맞지 않음
  - 최적의 threshold를 찾아야 한다.
  - 활용 시나리오마다 더 비싼 실수가 다르다.
    - 확인 연락 : 연락 비용은 적고, 취소를 놓치면 빈 방이 생긴다 -> 놓치는 쪽이 비쌈
    - 선제 재판매 : 안 올 줄 알았던 고객이 오면 방이 없다 -> 잘못 고르는 쪽이 비싸다
    따라서 하나의 threshold로 모든 활용에 맞출 수 없다.
    모델은 취소 위험 순위를 얼마나 잘 매기는지로 평가하고, threshold는 활용 단계에서 시나리오별로 정한다


## 3. 데이터
- 데이터 출처 : hotel booking demand datasets (https://www.kaggle.com/datasets/jessemostipak/hotel-booking-demand)
- 수집 기간 : 2015년 7월 1일 ~ 2017년 8월 31일 (약 2년 2개월)
- 데이터 규모 : 예약 기록 119,390건, 32개 피처
- 대상 호텔 유형
  - `Resort Hotel` : 포르투갈 남부 알가르브(Algarve) 휴양지에 위치한 리조트 호텔
  - `City Hotel` : 리스본(Lisbon) 도심에 위치한 비즈니스/관광 호텔
- 타겟 변수 :  `is_canceled` (고객의 최종 예약 취소 여부)
  - 0 : 정상 체크인, 투숙 완료
  - 1 : 예약 취소 또는 No-Show

## 4. 데이터 전처리
### 4-1. 데이터 타입 정리
- 데이터에 결측치가 "NULL" 문자열로 들어 있어 결측치로 처리
- agent, company 피쳐는 숫자로 저장되어 있지만 의미는 대리점·회사
- ID 피쳐 : 수치형을 범주형으로 변환

### 4-2. 누수 열 제거 — 예약 시점에 알 수 없는 값
| 열 | 제거 이유 |
|---|---|
| `reservation_status` | 최종 예약 상태. 정답과 같은 피쳐 |
| `reservation_status_date` | 취소일 또는 체크아웃일. 정답이 드러난 피쳐 |
| `assigned_room_type` | 체크인할 때 배정되는 객실 |
| `required_car_parking_spaces` | 주차 요청. 도착 후 기록되는 값 |
| `booking_changes` | 추출 시점까지 누적된 최종값 |

### 4-3. 중복 행
- 완전히 똑같은 행 31,994개 발견. 오류가 아니라 익명화 때문에 같은 조건의 단체 예약이 같은 행이 된 것으로 확인
- 삭제하면 단체 예약 비중이 왜곡되므로 유지
- 같은 행 뭉치가 학습과 평가 set에 나뉘지 않게 도착일 기준으로 분할

### ★4-4. 결측 처리 · 인코딩 (Pipeline 안에서 학습 데이터 기준으로만 학습)
| | 선형 모델 (LogReg) | 트리 모델 (RF, LightGBM 등) |
|---|---|---|
| 수치형 결측 | 중앙값 대체 | 중앙값 대체 |
| 수치형 스케일 | 표준화 | 없음 (트리는 크기 비교만 하므로) |
| 범주형 결측 | `"missing"` 범주로 대체 | `"missing"` 범주로 대체 |
| 범주형 인코딩 | 원-핫 | 정수 코드
| 희귀 범주 (20건 미만) | 하나로 묶음 | 하나로 묶음 |
| 처음 보는 범주 (미래 데이터) | 희귀 범주로 처리 | 별도 코드(-1)로 처리 |

- 결측을 `"missing"` 범주로 둔 이유: `agent`가 비어 있으면 대리점 없이 직접 예약했다는 뜻이고,
  `company`가 비어 있으면 개인 예약 정보이다.
- Pipeline으로 묶은 이유: 중앙값과 범주 목록을 학습 데이터에서만 계산해서,
  평가 데이터의 정보가 전처리에 섞이지 않게 하기 위함.
  Pipeline: [ID 열 변환] → [결측 대체 · 인코딩 · 표준화] → [모델]

시간 분할을 해야하는 데이터라서 테스트 기간에 학습 때 본 적 없는 agent나 country가 나올 수도 있음
학습 데이터 기준으로 범주 목록을 만들어두면 처음 보는 범주는 모르는 값으로 처리된다.



파이프라인으로 학습 데이터에서만 계산해서 평가 기간 정보가 전처리에 섞이지 않게 했다.


## 5. EDA 주요 인사이트

### 5-1. 타깃과 호텔 유형
- 타겟 변수 비율이 유지 63 : 취소 37로 극단적 불균형은 아니지만, 정확도만으로는 판단할 수 없음. 다른 지표를 평가지표로 삼아야 한다.
- 예약의 66%가 City Hotel이고, 취소율의 경우 City 41.7% vs Resort 27.8%로 각 호텔별 차이가 크다.
  - `hotel`은 기본 피처로 사용. 두 호텔의 취소 방식이 다를 수 있다는 점을 염두해 둔다.

### 5-2. 중복 행 발견
- 31,994행(전체 데이터의 26.8%)이 다른 행과 모든 값이 같다. 가장 큰 묶음은 180건
  (City Hotel, 단체, Non Refund, 277일 전 예약, 전부 취소).
- 오류가 아니라 익명화의 결과임을 확인. 예약 번호, 고객 이름이 지워져 같은 조건의 일괄 예약이 똑같은 행이 된 것으로 확인하였다.
- 중복 행은 단체, Non Refund 비율이 높고 취소율이 58.4%로, 여행사의 대량 선점 후 일괄 취소 패턴으로 보인다.
  - 삭제하지 않고 같은 행이 학습과 평가 set에 나뉘지 않도록 분할 방식을 정해야 한다.

### 5-3. 누수는 단일 열 점검만으로는 다 보이지 않는다
- 단일 열 AUC로는 `reservation_status`(1.0)만 확실히 드러났다.
- `reservation_status_date`(0.76), `assigned_room_type`(0.60)은 혼자 보면 평범하지만
  도착일·예약 객실과 비교하면 정답이 드러난다 (배정 객실이 바뀐 예약의 취소율 5% vs 42%).
- `required_car_parking_spaces`는 94%가 0이라 AUC로 안 보였지만,
  **주차 요청 7,416건 중 취소 0건** → 범주별 취소율을 봐야 보인다.
  → 열마다 **"언제 기록되는 값인가"**를 따져 제거 여부를 판단했다.

### 5-4. 환불 불가인데 취소율 99%
- `deposit_type = Non Refund`의 취소율이 99%. 개인 고객 행동으로는 설명이 안 된다.
- Non Refund 예약은 98%가 중복 행, 97%가 포르투갈, 88%가 City Hotel
  → 여행사 단체 계약 조건이 보증금 유형으로 기록된 것으로 추정.
- 취소 예약의 62%가 포르투갈(PRT)인 반면 유지 예약은 28%만 PRT. 같은 단체 예약 패턴이 국가 통계에도 섞여 있다.
  → 두 열 모두 예약 시점 값이라 유지하되, 특정 여행사 관행에 의존하는 한계로 기록.

### 5-5. 호텔 비즈니스 특성에 따른 계절성
- 이 데이터에는 7~8월 성수기가 두 번 반복되는 계절성이 있다.
- 월별 취소율이 21%~44% 범위로 들쭉날쭉하고, 2017년 4~6월은 43~44%로 취소율이 높은 편이다.
- 과거로 학습해서 미래를 예측하는 상황이므로, 도착일 기준 시간 분할로 평가한다.
  학습 기간(~2016) 취소율 36.2% vs 테스트 기간(2017-05~08) 40.5%.

## 6. 피처 엔지니어링
- 피쳐 다루는 기준 통일
  - '예약 시점'에 알 수 있는 값으로만 만든다.
  - 추가·제거 여부는 검증 기간(2017-01월 ~ 04월, 과거 데이터) 점수로만 판단한다. 테스트 기간(2017-05월 이후, 미래 데이터)은 보지 않는다.

### 6-1. 파생 피처 추가
| 피처 | 정의 | 의도 |
|---|---|---|
| `total_nights` | 주말 + 주중 숙박일 | 단기 출장 vs 장기 여행 |
| `total_guests`, `has_kids` | 총 인원 / 아이·유아 동반 여부 | 가족 여행은 일정 변경이 어렵다 |
| `arrival_weekday` | 도착 요일 | 주말 레저 vs 주중 출장 |
| `via_agent`, `via_company` | 대리점·회사 경유 여부 | ID 수백 개 대신 경유 여부만 |
| `adr_per_person` | 1인당 1박 요금 | 객실 요금은 인원수에 따라 왜곡됨 |
| `prev_cancel_ratio` | 과거 예약 중 취소 비율 | 과거 취소 '횟수'보다 '성향' |

- 결과 : 효과 없음 (검증 ROC-AUC ±0.001)
  - 모두 원래 열에서 쉽게 계산되는 값이라, 모델이 이미 열 조합으로 알아내고 있던 것으로 보인다.

### 6-2. 날짜 열 제거 : 성능 __% 개선
| 열 | 제거 이유 | 효과 |
|---|---|---|
| `arrival_date_year` | 미래 구간은 학습 때 본 적 없는 연도 | 연도별 취소율을 외워도 미래엔 쓸 수 없음 |
| `arrival_date_week_number` | 같은 주차라도 해마다 날짜·요일이 다름 → 트리가 특정 주를 외움 | LightGBM 검증 ROC-AUC +0.011 |
- 계절성은 `arrival_date_month`로 충분하다. 선형 모델은 차이 없음 → 외우는 문제는 트리에서만 생김.

### 6-3. 예약 후 기록되는 열 제거 — 점수를 잃더라도 뺀다
| 열 | 제거 이유 | 효과 |
|---|---|---|
| `required_car_parking_spaces` | 주차 요청 7,416건 중 취소 0건 → 도착 후 기록 | |
| `booking_changes` | 추출 시점까지 누적된 최종값 | 둘 합쳐 LightGBM −0.010, LogReg −0.014 |
- 떨어진 점수만큼은 **원래 가짜 성능**이었다고 판단. 테스트 점수를 본 뒤에도 되돌리지 않았다.

### 6-4. 최종 피처
- 원본 32열 → 누수 5개·날짜 2개·타깃 제거 → 파생 피처 9개 추가 → **최종 32개**
(`src/data.py`의 `final_features()` 한 줄로 재현)
- 피처를 더하는 것보다 제거하는 것이 성능과 신뢰도를 더 크게 바꿨다.
- 3개의 부스팅 모델(LightGBM·XGBoost·CatBoost)도 0.900~0.902로 동률이었다.
  - 본 데이터에서는 알고리즘 비교보다 어떤 피처를 쓰고 어떻게 평가하느냐가 중요함을 확인하였다.

## 7. 모델링
### 7-1. 베이스라인
| 모델 | 역할 | 선택 이유 |
|---|---|---|
| Dummy (항상 '유지') | 바닥 기준선 | 모델 없이 낼 수 있는 점수. ROC-AUC 0.5, PR-AUC = 취소율 |
| 로지스틱 회귀 | 출발점 | 계수로 어떤 피처가 취소를 올리고 내리는지 바로 해석 가능 → 1일차 누수·피처 점검에 적합 |
| 띠용 | 때용 | 확률을 출력하므로 ROC-AUC·PR-AUC로 평가 가능 |
| 띠용 | 때용 | 선형 모델의 한계를 기준으로 삼아, 이후 트리 모델이 비선형 관계로 얼마나 더 얻는지 측정 |


### 7-2. 비교 모델 — 계열별 대표
| 계열 | 모델 | 비교한 설정 | 넣은 이유 |
|---|---|---|---|
| 선형 | 로지스틱 회귀 | — | 베이스라인 |
| 배깅 | RandomForest | `min_samples_leaf` 1 / 5 | 트리 앙상블의 기본형. 행을 외우는 정도 확인 |
| 부스팅 | LightGBM | `num_leaves` 31 / 63 / 127, subsample | 정형 데이터의 표준 모델, 빠름 |
| 부스팅 | XGBoost | `max_depth=6` | 같은 계열 다른 구현. 트리 수·학습률은 LightGBM과 맞춤 |
| 부스팅 | CatBoost | `depth=6` | 범주형 처리에 강함 (`country`, `agent` 등 범주가 많음) |

- 하이퍼파라미터는 대표값 몇 개만 비교했다. 검증 기간 하나로 촘촘히 튜닝하면 그 기간에 과적합되기 때문이다.

|---|---|---|---|

| CatBoost (depth=6) | 0.902 | 0.855 | 11s |
| XGBoost (max_depth=6) | 0.901 | 0.856 | 2s |
| LightGBM (num_leaves=127) | 0.894 | 0.849 | 3s |
| RandomForest (min_samples_leaf=5) | 0.888 | 0.840 | 4s |
| 로지스틱 회귀 | 0.872 | 0.826 | 2s |

- 부스팅 > 배깅 > 선형 순. 피처 간 상호작용과 비선형 관계를 부스팅이 가장 잘 잡는다.
- 잎 수를 늘리면(31 → 127) 오히려 떨어진다 → 복잡도는 31로 충분.
- 부스팅 3종이 0.900~0.902로 **동률**.

### 7-4. 최종 선택: LightGBM (`num_leaves=31`, `n_estimators=500`, `learning_rate=0.05`)
- 성능이 비슷하여 더 단순하고 빠른 모델을 채택.
  - CatBoost는 0.001 높지만 학습이 약 6배 느리다. 이 차이는 잡음 수준이다.
  - subsample 추가 이득(+0.0007)도 잡음 수준이라 기본 설정을 유지.
- 매달 재학습이 필요한 상황(성능이 시간에 따라 떨어짐)이라 학습 속도가 실제로 중요하다.

### 7-5. 테스트 기간 최종 평가 (2017-05~08, 1회)

## 8. 결과 및 해석
최종 LightGBM이 무엇을 근거로 판단하는지 테스트 기간(2017-05~08)에서 확인한다.
두 가지 방법을 같이 쓴다.
- **Permutation importance**: 열 하나를 섞었을 때 ROC-AUC가 얼마나 떨어지나 → 성능에 대한 실제 기여
  (LightGBM 내장 중요도는 범주가 많은 열·연속형 열을 과대평가하므로 쓰지 않음)
- **SHAP**: 예측 하나하나를 피처별 기여로 분해 → 기여의 크기와 **방향** (테스트 5,000건, log-odds 단위)

### 8-1. 무엇을 보나 — 중요도 상위 5
| 순위 | Permutation (ROC-AUC 감소) | SHAP 비중 |
|---|---|---|
| 1 | `country` 0.100 | `deposit_type` 25% |
| 2 | `market_segment` 0.074 | `country` 16% |
| 3 | `deposit_type` 0.070 | `market_segment` 11% |
| 4 | `agent` 0.060 | `total_of_special_requests` 9% |
| 5 | `total_of_special_requests` 0.045 | `lead_time` 8% |

- 상위권은 **"어떤 경로·조건으로 예약했나"**(보증금 조건, 유통 채널, 대리점, 국적)이고,
  그다음이 **고객 행동 신호**(특별 요청, 리드타임)다.
- 두 방법의 1등이 다른 이유: Non Refund는 테스트 데이터의 약 9%뿐이라 섞어도 영향받는 행이 적지만(Permutation),
  해당 행에서는 기여가 매우 크다(SHAP).
- 2일차 파생 피처(`adr_per_person`, `total_nights` 등)는 기여가 작다. 6장 결과(±0.001)와 일치.

### 8-2. 어느 방향으로 보나 — 범주별 평균 SHAP
| 피처 | 값 | 평균 SHAP | 방향 |
|---|---|---|---|
| `deposit_type` | Non Refund | **+6.6** | 사실상 "무조건 취소" |
| `country` | PRT (포르투갈) | +1.3 | 취소 쪽 |
| `country` | GBR · FRA · DEU | −0.9 ~ −1.2 | 유지 쪽 |
| `market_segment` | Online TA | + | 취소 쪽 |
| `market_segment` | Groups | −0.47 | 유지 쪽 (실제 취소율은 66%) |
| `customer_type` | Contract · Group | − | 유지 쪽 |

- **Groups의 역설**: 실제 취소율은 66%로 높은데 SHAP은 음수다.
  단체 예약의 높은 취소는 이미 `deposit_type`(Non Refund)이 설명하고 있어서,
  *보증금 조건이 같다면* 단체라는 사실 자체는 유지 쪽이다.
  SHAP은 **다른 피처를 감안한 뒤의 기여**라서 단순 취소율과 다를 수 있다.

### 8-3. 수치형 피처의 효과
| 피처 | 효과 |
|---|---|
| `lead_time` | 직전 예약(2~3주 이내)은 강하게 유지 쪽. 20~30일 근처에서 중립을 지나고, 100일 이후로는 완만 |
| `total_of_special_requests` | 0개 → 1개에서 유지 쪽으로 **급격히** 이동. 요청을 남긴 고객은 올 생각이 있는 고객 |
| `adr` (1박 요금) | 효과가 작고 방향이 섞여 있음 → 요금 자체는 취소를 크게 좌우하지 않음 |

### 8-4. 해석 정리
- 모델 판단의 **40% 이상이 `deposit_type`과 `country`** 두 열에서 나온다.
- 두 열 모두 2일차에 일반화 위험으로 기록한 열이다.
  - Non Refund 99% 취소 = 특정 여행사의 단체 예약 일괄 취소 관행
  - PRT의 높은 취소 = 체크인 안 한 예약에 국적 기본값이 남았을 가능성
- 즉 모델 성능의 상당 부분이 **이 데이터 기간의 여행사 관행과 기록 방식**에 기대고 있다.
  관행이 바뀌면 성능이 크게 떨어질 수 있으므로, 운영 시 세그먼트별 성능 모니터링이 필요하다.
  - 예시 : 띠용 때용

## 9. 비즈니스 활용 방안

### 9-1. 먼저 확인: 예측 확률을 그대로 믿어도 되나
- 순위(ROC-AUC)는 좋아도 확률 값 자체가 틀릴 수 있다. threshold와 건수 예측은 확률 값을 쓰므로 먼저 확인한다.
- 모델은 취소 확률을 **낮게 예측**한다.
  - 테스트 기간 평균 예측 33.9% vs 실제 40.5%
  - 0.1~0.6 구간에서 최대 15%p 차이. 0.8 이상의 확신 구간은 대체로 맞다.
- 원인: 테스트 기간 취소율(40.5%)이 학습 기간(36.2%)보다 높아졌는데, 모델이 이 변화를 따라가지 못했다.
  → threshold는 이론값을 쓰지 않고 **검증 기간에서 직접 찾는다.** 건수 예측은 과소 추정을 감안해서 읽는다.

### 9-2. 시나리오별 threshold
비용은 **빈 방 1개 = 1** 기준의 **가정값**이다. 실제 값은 호텔이 정해야 한다.

| 시나리오 | 양성으로 표시하면 | 오탐(FP) 비용 | 놓침(FN) 비용 |
|---|---|---|---|
| A. 확인 연락 | 도착 전 리마인드·재확인 | 1/5 (연락 비용) | 1 (빈 방) |
| B. 선제 재판매 | 해당 객실을 미리 다른 고객에게 판매 | 4 (온 손님 방이 없음 → 보상·평판) | 1 (빈 방) |

검증 기간(2017-01~04)에서 예약당 비용이 최소가 되는 threshold를 고르고, 테스트 기간에 그대로 적용했다.

| 시나리오 | threshold | 표시 비율 | Precision | Recall | 예약당 비용 (0.5 대비) |
|---|---|---|---|---|---|
| A. 확인 연락 | **0.10** | 67% | 0.58 | **0.96** | 0.892 → 0.367 (**−59%**) |
| B. 선제 재판매 | **0.85** | 11% | **0.98** | 0.26 | 0.396 → 0.309 (**−22%**) |

- 두 시나리오 모두 기본값 0.5는 최적이 아니다. **threshold는 모델이 아니라 비즈니스 비용이 정한다.**
- 검증에서 고른 값이 테스트의 사후 최적값과 거의 같다 (A 0.10 vs 0.09, B 0.85 vs 0.86) → 기간이 바뀌어도 안정적.

### 9-3. 연락 인력이 한정될 때 — 상위 k%만 연락
- 시나리오 A는 예약의 67%에 연락해야 해서 현실적이지 않을 수 있다.
- 대신 취소 확률 **순위 상위 k%만** 연락한다. 순위만 쓰므로 확률 과소 추정의 영향을 받지 않는다.

| 연락 범위 | Precision | Recall | 무작위 대비 |
|---|---|---|---|
| 상위 10% | 0.99 | | |
| 상위 20% | 0.86 | 0.43 | 2.1배 |

### 9-4. 날짜별 취소 건수 → 초과 예약 규모
- 초과 예약은 개별 예약이 아니라 **"그날 몇 건이 취소될까"**로 정한다.
- 예약별 취소 확률을 호텔·도착일별로.

| | 결과 |
|---|---|
| 날짜별 증감 추적 | 실제 취소 건수와 **상관 0.97**. City Hotel의 대량 취소일(200건 안팎)도 거의 정확 |
| 전체 수준 | 하루 평균 약 6건(**16%
| 호텔별 | City −8%, **Resort −37%** |

- 그대로 쓰면 **덜 초과 예약**하게   고, 빈 방이 조금 남는 쪽으로 틀린다.
- 쓰려면 **호텔별로 확률을 재보정**해야 한다. 특히 Resort.

### 9-5. 운영 시 주의할 점
- **시나리오 B는 사실상 "여행사 블록 예약 초과 판매" 규칙이다.**
  B에서 고른 예약의 84%가 Non Refund, 87%가 포르투갈이다.
  여행사 계약 관행이 바뀌면 바로 무너진다.
  → 이 세그먼트(Non Refund · PRT · 단체)의 실제 취소율을 따로 모니터링하고,
    취소율이 떨어지면 재학습 전까지 시나리오 B를 **중단**한다.
- **성능이 시간에 따라 떨어진다** (테스트 5월 0.908 → 7·8월 0.83).
  → 매달 재학습, 최근 데이터로 확률
- **비용은 가정값이다.**
  → 실제 객실 단가와 보상 비용으로 다시 계산해야 threshold가 확정된다.
